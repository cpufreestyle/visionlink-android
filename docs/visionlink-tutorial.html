01 / OVERVIEW

项目是什么 · 五种模式What VisionLink Does

VisionLink 是一款为视障人士打造的 AI 辅助导盲 App。核心思路很朴素：让手机（乃至智能眼镜）替使用者"看"，再把看到的东西用语音说出来。它把摄像头、端侧 AI 模型、云端大模型、蓝牙戒指、Rokid 智能眼镜五样东西串成一条链路。

三端硬件

终端 · A

Android 手机

主控中枢。摄像头采集、AI 推理调度、语音播报、所有逻辑都在这里。即使不接任何外设也能独立工作。

终端 · B

Rokid CXR-L 眼镜

可选外设。提供第一视角摄像头 + HUD 抬头显示 + 触控板/语音交互，解放双手。

终端 · C

BLE 蓝牙戒指

可选外设。一个物理按键，单击/双击/长按触发不同操作，盲人不必摸屏幕。

五种功能模式

App 用一个整型变量 currentMode 表示当前处于哪种模式。前三种是"拍一张分析一次"，模式 4 是实时连续，"连续检测"是叠加在模式之上的开关。

模式名称做什么用什么引擎
1障碍物检测识别前方障碍物 + 方位 + 距离，提示避让端侧 YOLO / 云端大模型
2文字识别读出画面里的文字（招牌、菜单、说明书）ML Kit OCR / 云端
3场景描述用一段话描述"眼前是什么场景"云端多模态大模型
4指向引导实时检测手指与目标物，语音引导手去够到物体端侧 HandLandmarker + 目标检测
叠加开关 · 连续检测：让模式 1 每隔几秒自动拍一次，无需反复手动触发
学习提示

读这个项目最好的顺序是：先理解一次拍照 → 分析 → 播报的主循环（第 4 章），它是整个 App 的心跳；其余所有功能（眼镜、戒指、语音、云端）都只是在这条主循环的入口或出口上做文章。

02 / ARCHITECTURE

整体架构 · God Activity + ManagerOne Big Activity, Many Managers

这个项目刻意没有用 MVVM、没有 Fragment、没有依赖注入框架。它选了一种"老派但直接"的结构：一个巨型 Activity 当总指挥，一堆 Manager 各管一摊。对于学习者，这反而是好事——数据流清晰可追，不用在框架的抽象层里绕。

MainActivity —— "上帝对象"

MainActivity.kt（约 1600+ 行）持有所有 Manager 的引用，负责：初始化、UI 绑定、模式切换、把各个入口的事件路由到主循环。它就是那根把所有零件串起来的轴。

MainActivity 持有的核心 Manager
class MainActivity : AppCompatActivity() {
    private lateinit var cameraManager: CameraManager      // 摄像头采集
    private lateinit var aiManager: AIInferenceManager     // AI 推理调度（端/云）
    private lateinit var ttsManager: TtsManager             // 语音播报
    private lateinit var speechManager: SpeechManager       // 语音命令识别
    private var glassesManager: CXRGlassesManager? = null    // Rokid 眼镜（可选）
    private var ringManager: BleRingManager? = null          // 蓝牙戒指（可选）
    private var handGuide: HandGuideManager? = null          // 指向引导（模式4）
    private var currentMode: Int = 1                     // 当前模式 1/2/3/4
}

Manager 分工一览

Manager / 类职责关键依赖
CameraManager用 CameraX 采集画面，把每一帧变成 Bitmap 回调出去CameraX ImageAnalysis
AIInferenceManager推理总调度，决定这一帧交给哪个引擎（YOLO/云端）YoloDetector · OkHttp
YoloDetector端侧目标检测（EfficientDet COCO80）MediaPipe Tasks Vision
HandGuideManager模式4：手部关键点 + 目标物，算相对方位MediaPipe HandLandmarker
OcrRecognizer模式2：图片文字识别ML Kit Text Recognition
TtsManager把结果文本读出来Android TextToSpeech
SpeechManager把用户说的话转成命令Android SpeechRecognizer
CXRGlassesManagerRokid 眼镜授权/连接/HUD/交互回调Rokid CXR-L SDK
BleRingManager扫描/连接戒指，把按键事件回调出去BLE GATT
VoicePrintManager声纹注册与比对ONNX Runtime
为什么这样设计

对一个"设备强相关、逻辑线性"的 App 来说，每个 Manager 封装一类硬件/能力，Activity 只做编排，是最容易维护和调试的方式。代价是 Activity 会变得很大（God Activity），但换来的是一眼能看到全貌。

03 / STARTUP

启动流程 · 那次闪退是怎么修的onCreate & The Crash We Fixed

v5.9.5 一启动就闪退。排查过程本身就是一堂课，我先讲真正的根因，再讲正常的启动流程。

崩溃根因：MaterialButton 撞上非 Material 主题

抓 adb logcat 才看到真相：布局里用了 MaterialButton，但 AndroidManifest.xml 的主题是 Theme.AppCompat.Light.DarkActionBar。MaterialButton 强制要求宿主主题是 MaterialComponents 系，否则一 inflate 就抛异常，整个 Activity 起不来。

修复 · AndroidManifest.xml（Bridge 主题：保留 AppCompat 外观，同时支持 Material 组件）
// 修复前 —— MaterialButton 无法 inflate，启动即崩
android:theme="@style/Theme.AppCompat.Light.DarkActionBar"

// 修复后 —— Bridge 主题两全其美
android:theme="@style/Theme.MaterialComponents.Light.DarkActionBar.Bridge"
踩坑复盘

我一开始误判成 native .so 库 16KB 页对齐问题，绕了很大一圈。教训：崩溃排查第一步永远是抓真实 logcat，而不是凭"最近改了什么"猜。日志一到，根因五秒钟就现形。

正常启动：onCreate 全流程

修复的同时，给 onCreate 套了一层降级不闪退的保护——任何一步初始化失败都不让整个 App 挂掉，而是记录并继续。

MainActivity.onCreate —— 用 try/catch(Throwable) 兜底
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_main)
    try {
        initManagers()        // 1. 实例化所有 Manager
        setupUI()             // 2. 绑定按钮/模式切换
        setupDebugCommands()  // 3. 调试命令
        observeAIState()      // 4. 监听 AI 状态变化
        checkPermissions()    // 5. 请求相机/麦克风等权限
        checkForAppUpdate()   // 6. 检查 GitHub Release 有无新版
    } catch (t: Throwable) {
        // 关键：catch Throwable 而非 Exception
        // UnsatisfiedLinkError 是 Error 不是 Exception，catch(Exception) 抓不住
        Log.e(TAG, "onCreate 初始化失败，进入降级模式", t)
        CrashReporter.reportError("onCreate", t.message ?: "", t)
    }
}
Kotlin 细节

UnsatisfiedLinkError（加载 .so 失败）继承自 Error 而不是 Exception。所以项目里凡是加载 native 模型的地方，catch 全部从 Exception 改成了 Throwable——这是一个新手极易踩、且 IDE 不会警告的陷阱。

启动顺序为什么重要

1setContentView —— 先把布局撑起来（这一步崩了就是上面的主题问题）
↓
2initManagers —— Manager 之间有依赖，被依赖的先建（如 TTS 先于用它的模块）
↓
3checkPermissions —— 相机权限拿到后，才真正 startCamera；没权限时 UI 仍可用
↓
4autoInitYolo —— 后台异步加载端侧模型，不阻塞主线程，失败降级到云端
04 / THE CORE LOOP

核心数据闭环 · 从拍照到播报Camera → Inference → Speech

这是整个 App 的心跳。理解了它，其余全是枝叶。一次完整循环长这样：

①触发 —— 用户点屏幕 / 按戒指 / 说命令，最终都调用 captureAndAnalyze()
↓
②取帧 —— CameraManager 从最新一帧拿到 Bitmap
↓
③推理 —— AIInferenceManager 按当前模式选引擎，产出一段结果文本
↓
④输出 —— TtsManager 读出来 + 眼镜 HUD 显示（如已连接）

①→② 取一帧画面

CameraX 的 ImageAnalysis 用 STRATEGY_KEEP_ONLY_LATEST 策略——只保留最新一帧，处理不过来就丢旧帧，保证"拍的就是当下"。每帧通过 ImageProxy 回调，转成 Bitmap 后必须 close() 释放，否则相机会卡死。

CameraManager —— 分析器回调
imageAnalysis.setAnalyzer(executor) { imageProxy ->
    try {
        val bitmap = imageProxy.toBitmap()   // 转 Bitmap
        latestBitmap = bitmap                // 缓存"最新一帧"供拍照取用
        frameCallback?.invoke(bitmap)        // 连续模式下逐帧回调（模式4用）
    } finally {
        imageProxy.close()                   // 必须关闭，否则相机管线阻塞
    }
}
真实存在的坑

toBitmap() 没有传入 rotationDegrees 做旋转矫正。竖屏拿手机时，送进模型的画面可能是躺倒的，直接影响检测准确率。这是待修问题之一（见第 11 章）。

③ 按模式选引擎推理

核心调度在 AIInferenceManager。它内部有一个 currentEngine，用 when 分发——注意：这些引擎是"互斥"的，不是"协同"的。同一时刻只有一个引擎在跑。

AIInferenceManager —— 障碍物检测的分发
suspend fun detectObstacles(bitmap: Bitmap): String {
    return when (currentEngine) {
        Engine.YOLO      -> yoloDetector.detect(bitmap)        // 端侧，快、免费、离线
        Engine.STEPFUN   -> runStepFunInference(bitmap, mode)  // 云端多模态大模型
        Engine.LM_STUDIO -> runLocalServerInference(bitmap)    // 局域网自建服务
        Engine.EDGE      -> edgeModel.infer(bitmap)
    }
}
这里藏着你要做的功能

你的图2 目标是"端云协同"：端侧模型先提取信息，再把这些信息喂给云端大模型联合分析。但现在代码是 when 二选一，端和云永远不会同时出现在一次推理里。这正是需要改造的关键缺口，第 11 章会详细拆解。

④ 输出：语音 + HUD 双通道

结果拿到后，走两条并行的输出通道：手机 TTS 一定播，眼镜 HUD 在已连接时同步显示。

结果回到 UI 线程后的双通道输出
runOnUiThread {
    ttsManager.speak(result)                // 通道 A：手机语音
    glassesManager?.showResult(result)      // 通道 B：眼镜 HUD（未连接时内部直接 return）
}
待修问题预告

TTS 目前用的是默认 QUEUE_ADD 而非 QUEUE_FLUSH——连续检测时多条结果会排队堆积，说完一长串旧的才轮到新的，实时性差。另外"未检测到障碍"这类话术对盲人有误导性安全暗示，也在待改清单里。

05 / EDGE AI

端侧 AI · 在手机上跑的三个模型On-Device Models: YOLO / Hand / OCR

端侧 AI 的价值：快、免费、离线、不上传隐私。项目里有三个跑在手机本地的模型。

① YoloDetector —— 目标检测

用 MediaPipe Tasks Vision 的 ObjectDetector，模型是 EfficientDet-Lite0，训练自 COCO 数据集（80 类常见物体：人、车、椅子、瓶子……）。它给出每个物体的类别 + 边界框 + 置信度。

从边界框推出"方位"和"距离"
// 方位：看边界框中心 X 落在画面左/中/右
fun directionPhrase(centerX: Float, width: Int): String {
    return when {
        centerX < width * 0.33 -> "左前方"
        centerX > width * 0.67 -> "右前方"
        else                    -> "正前方"
    }
}

// 距离：用"假设物体真实高度 1 米"反推 —— 粗略估计
fun estimateDistance(boxHeightPx: Float, imageHeightPx: Int): Float {
    val assumedRealHeightM = 1.0f
    return assumedRealHeightM * imageHeightPx / boxHeightPx  // 只是数量级参考
}
局限性

距离估算假设所有物体都是 1 米高，对瓶子、台阶完全不准，只能给"近/远"的数量级感觉。要精确得靠深度传感器或双目——当前是刻意的工程折中。

② HandLandmarker —— 手部关键点（模式4的核心）

MediaPipe 的 HandLandmarker 能吐出手上 21 个关键点的坐标。项目关心的是 landmark 8 = 食指指尖。模式4"指向引导"就是：同时检测食指指尖和目标物，算出"物体在手指的哪个方向、还差多远"，实时语音引导手去够。

HandGuideManager —— 指尖坐标（landmark 8）
val indexTip = handLandmarks[8]   // 21 点中第 8 个 = 食指指尖
val dx = targetX - indexTip.x()
val dy = targetY - indexTip.y()
// 由 (dx, dy) 生成"向左一点""再往上""快碰到了"等引导语
真实并发坑

HandGuideManager 的 processFrame() 和 release() 存在竞态：一帧还在推理时若触发释放，可能访问已释放的 native handle。已确认，是待修问题。

③ OcrRecognizer —— 文字识别（模式2）

用 ML Kit 的 Text Recognition。但这里有个大问题：代码注释声称支持中文，实际却用了 TextRecognizerOptions.DEFAULT_OPTIONS——那是拉丁文识别器，识别不了中文。

OcrRecognizer —— 注释与实现不符
// 注释说"支持中文识别"，但……
val recognizer = TextRecognition.getClient(
    TextRecognizerOptions.DEFAULT_OPTIONS   // ← 这是 latin-only！中文识别为空
)
// 要中文应换成 ChineseTextRecognizerOptions.Builder().build()
// 并加依赖 com.google.mlkit:text-recognition-chinese
待修 Bug

对一个中文场景的导盲 App，"读不了中文招牌"是硬伤。修法是换成 ChineseTextRecognizerOptions 并加对应依赖；或者干脆把模式2也走云端多模态大模型（顺带能读手写体和艺术字）。

06 / INTERACTION

三种交互入口 · 殊途同归Touch / Ring / Voice → One Entry

盲人不方便看屏幕，所以 App 提供三条并行的触发通道，最终都汇聚到同一个 captureAndAnalyze()。这是很优雅的设计——入口多样，主干唯一。

入口 A

触摸屏

屏幕大按钮，明眼人协助或低视力用户可用。setupUI() 里绑定 onClick。

入口 B

蓝牙戒指

物理按键，单击/双击/长按三种手势。盲人首选，无需触屏。

入口 C

语音命令

说"看看前面""读一下"，SpeechManager 转成命令。

戒指事件：一个键，三种手势

BleRingManager 通过 BLE GATT 收到按键，回调给 Activity 的 handleRingEvent。注意——BLE 回调发生在 Binder 线程，操作 UI/相机必须切回主线程，所以每个分支都包在 runOnUiThread 里。

MainActivity.handleRingEvent —— 手势路由（已验证不会崩）
fun handleRingEvent(event: RingEvent) = runOnUiThread {
    when (event) {
        RingEvent.SINGLE_CLICK -> captureAndAnalyze()      // 单击：拍照分析（主干入口）
        RingEvent.DOUBLE_CLICK -> cycleMode()              // 双击：切换模式
        RingEvent.LONG_PRESS   -> toggleContinuousMode()   // 长按：开/关连续检测
    }
}
已知逻辑缺口

cycleMode() 写的是 if (currentMode >= 3) 1 else currentMode + 1——只在 1/2/3 之间循环，永远切不到模式4（指向引导）。用戒指的盲人无法进入模式4。这是需要修的边界问题。

BLE 连接的关键一步：CCCD 描述符

要收到戒指的按键通知，光 setCharacteristicNotification 不够——必须往 CCCD（0x2902 描述符）写入 ENABLE_NOTIFICATION，否则外设根本不发通知。这是 BLE 新手最常漏的一步。

BleRingManager.onServicesDiscovered —— 开启通知的两步
gatt.setCharacteristicNotification(characteristic, true)   // 第一步：本地开关
val cccd = characteristic.getDescriptor(CCCD_UUID)         // 0x2902
cccd.value = BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE
gatt.writeDescriptor(cccd)                                  // 第二步：告诉外设"请推送"
07 / SMART GLASSES

眼镜连接 · Rokid CXR-L 全流程Auth → Connect → HUD → Callback

Rokid 眼镜的接入比戒指复杂，因为它不是直接蓝牙，而是要经过 Rokid AI App 授权。CXRGlassesManager 封装了完整状态机。

连接状态机

1DISCONNECTED —— 检查 Rokid AI App 是否安装（没装直接报错引导安装）
↓
2AUTHENTICATING —— requestAuthorization 拉起 Rokid App 授权界面，拿 token
↓
3CONNECTING —— CXRLink.connect(token)，带 30 秒超时保护
↓
4CONNECTED —— configCXRSession(CUSTOMVIEW)，可以推 HUD 了
CXRGlassesManager —— 即时授权的快路径
val authResult = RokidCxrHelper.requestAuthorization(activity)
if (authResult.immediateToken != null) {
    // 之前授权过，SDK 直接返回 token，跳过用户操作
    connectionState = ConnectionState.CONNECTING
    connectWithToken(activity, authResult.immediateToken, onImmediateConnect)
} else if (authResult.started) {
    // 首次：授权 Activity 已弹出，等 onActivityResult 回来
}
超时保护的写法

连接用了双 job 竞速：一个真正 connect，一个 delay(30s) 计时；谁先完成谁生效，用 callbackCalled 标志位保证回调只触发一次。这是处理"可能永远不回来的异步操作"的经典模式，值得学。

HUD 显示 + 交互回调

连上后，眼镜是双向的：手机往 HUD 推文字（sendText），眼镜的触控板/语音也能反向触发命令（GlassesInteractionCallback）。updateHUDStatus 会把当前模式名 + 状态一起显示。

HUD 显示当前模式
fun updateHUDStatus(mode: Int, status: String) {
    val modeText = when (mode) {
        1 -> "障碍物检测"; 2 -> "文字识别"
        3 -> "场景描述"; 4 -> "指向引导"
        else -> "未知"
    }
    sendText("$modeText\n$status")
    setupFunctionIcons()  // 幂等：确保触控板功能图标可用
}
待补能力

目前眼镜主要用作输出（HUD）和触发（回调），但眼镜自带摄像头的画面还没接入主循环——你图2/图1 想要"眼镜第一视角拍照 → 分析"，需要补上 takePhoto 的图像回调链路（当前调用后拿不到图）。

08 / CLOUD INFERENCE

云端推理 · OpenAI 兼容多模态Vision API over HTTP

端侧模型只能识别 80 类物体、读不懂复杂场景。要"用一段话描述眼前"（模式3），必须靠云端多模态大模型。项目用的是 OpenAI 兼容格式——这意味着通义千问、GPT、Gemini、StepFun 等任何兼容此格式的服务都能直接对接，只改 baseURL 和 key。

09 / VOICEPRINT

声纹识别 · ECAPA-TDNNSpeaker Verification via ONNX

声纹用于区分是不是机主本人在说话（防止旁人误触发或用于个性化）。用的是 VoicePrintManager + ONNX Runtime，模型是语音领域经典的 ECAPA-TDNN，它把一段语音压成一个固定长度的向量（embedding）。

原理：把声音变成向量，比余弦相似度

1注册 —— 录一段机主的话，跑 ECAPA-TDNN 得到 embedding，存下来
↓
2验证 —— 新说一句，同样得 embedding
↓
3比对 —— 算两个向量的余弦相似度，超过阈值就认为是同一人
余弦相似度 —— 声纹比对的数学核心
fun cosineSimilarity(a: FloatArray, b: FloatArray): Float {
    var dot = 0f; var na = 0f; var nb = 0f
    for (i in a.indices) {
        dot += a[i] * b[i]
        na  += a[i] * a[i]
        nb  += b[i] * b[i]
    }
    return dot / (sqrt(na) * sqrt(nb))   // ∈ [-1,1]，越接近 1 越像同一人
}

10 / CONCURRENCY

协程与线程模型Coroutines: Main vs IO

这个 App 的线程规则其实很简单，记住三条就够：

规则 1

耗时活去 IO

模型推理、网络请求、文件读写 → Dispatchers.IO，绝不阻塞主线程。

规则 2

碰 UI 回主线程

更新界面、说话、操作相机 → Dispatchers.Main / runOnUiThread。

规则 3

回调线程要警惕

BLE 回调在 Binder 线程，SDK 回调线程不定 → 一律显式切回主线程再动 UI。

典型模式 —— withContext 在 IO 干活，切回 Main 更新
lifecycleScope.launch {                        // 默认 Main
    val result = withContext(Dispatchers.IO) {   // 切到 IO 跑推理
        aiManager.detectObstacles(bitmap)
    }
    // 回到 Main，直接更新 UI 安全
    ttsManager.speak(result)
    glassesManager?.showResult(result)
}
SupervisorJob 的作用

各 Manager 的 CoroutineScope 用了 SupervisorJob()——意思是一个子协程崩了，不会连坐兄弟协程。对"多个独立异步任务并行"的场景（眼镜连接 + AI 推理 + 声纹），这能避免一处异常拖垮全部。release() 时 scope.cancel() 统一收尾，防止内存泄漏。

B. 你要做的功能：端云协同（图2）

图2 的目标链路是：端侧模型提取信息 → 手机 App → 云端大模型联合分析 → 结果返回 → 手机/眼镜语音播报。而当前代码（第 4 章）里端和云是 when 二选一，从不协同。要落地图2，核心改造有四点：

改造 1

端侧结果注入云端 prompt

先跑 YOLO/HandLandmarker 拿到结构化信息（"左前方2米有椅子"），把它拼进云端 prompt，让大模型基于端侧线索做更准的判断，而不是纯靠图片。

改造 2

流式 SSE 边生成边播

把 .execute() 非流式改成 SSE 流式读取，按句子切分实时喂 TTS，把"干等数秒"变成"边说边出"。

改造 3

失败降级回端侧

云端超时/断网时，自动回退到纯端侧 YOLO 结果，保证"没网也能用"，符合导盲的安全底线。

改造 4

眼镜双通道 I/O

可选：用眼镜摄像头取第一视角图（改造问题9/10），结果同时走眼镜语音/HUD，真正解放双手。

端云协同的目标形态（示意）
suspend fun analyzeCollaborative(bitmap: Bitmap, mode: Int): Flow<String> = flow {
    // ① 端侧先提取结构化线索（快，不依赖网络）
    val edgeHints = yoloDetector.detect(bitmap)      // "左前方2米:椅子; 正前方:人"

    try {
        // ② 端侧线索注入云端 prompt，联合分析（流式）
        val prompt = "结合端侧检测[$edgeHints]，描述场景并给避障建议"
        cloudModel.streamVision(prompt, bitmap.toBase64Jpeg()).collect { chunk ->
            emit(chunk)                              // ③ 边生成边播报
        }
    } catch (e: Exception) {
        // ④ 云端失败 → 降级用端侧结果，保证可用
        emit(edgeHints)
    }
}
落地建议顺序

建议先修 A 清单里的高危两项（中文OCR、Hand竞态）+ 版本号硬编码，让现有功能稳；再做 改造1（端侧线索注入）——它不改架构、收益最大；然后 改造2（流式）提升体验；改造3（降级）保底线；眼镜双通道（改造4）作为最后的锦上添花。这是一条自底向上、每步可验证的路径。
